# A generated router and layer-4 network load balancer

## Appliance and interfaces

Deliver an installable Linux appliance for a controlled datacenter network. Two or more Ethernet interfaces route IPv4 and IPv6 between configured networks. Listener addresses can additionally distribute TCP and UDP traffic across backend pools. Ship Ethernet/VLAN parsing, neighbor discovery and expiry, longest-prefix forwarding, static routes and one interoperable routing-peer profile, per-interface policy, health checks, flow affinity, draining, stateful address translation, operator API/CLI, telemetry and a two-node availability mode. Specify the initial routing peer profile as BGP-4 unicast with explicit peer configuration, import/export policy and documented address-family capabilities. Unsupported protocol options receive defined protocol outcomes.

The author writes packet grammars, protocol and peer state machines, forwarding behavior, listener behavior, health/drain policy, flow allocation, configuration transactions and the management API in the executable appliance specification. The build produces a native packet processor, control daemon, generated CLI, schema/migration tooling and service units. Generic Linux drivers expose RX/TX buffers, queue ownership, timers, persistent records, authenticated management sockets and host interface configuration. NIC queues move frames; forwarding, route selection, flow binding, backend selection and failover decisions are generated application code.

## Packet and control semantics

| Authored subsystem | Specialized artifact | Dynamic data and ownership |
|---|---|---|
| Ethernet, VLAN, IPv4/IPv6, TCP/UDP and control-message grammars | Bounded parsers/encoders with proven read/write bounds and explicit failure decisions | Actual packet lengths, fields, interface, MTU and checksum/offload metadata |
| Route and neighbor programs | Longest-prefix table operations, next-hop selection, TTL/hop-limit handling, neighbor discovery and bounded queues | Routing information base, resolved forwarding snapshots, neighbor cache and current link state |
| Peer protocol and policy | Peer-session state machine, route import/export, selection and forwarding-table publication | Peer advertisements, withdrawals, timers and policy configuration |
| Virtual listeners and flows | Forward/reverse lookup, backend selection, address/port translation, checksum updates, idle expiry and counters | Flow identities, health generations, pool membership, port ownership and reverse bindings |
| Management and availability | Typed API/CLI, candidate validation, commit/rollback, readiness checks, leadership and replication protocol | Operator configuration, snapshot generations, connection state and fencing leases |

Define handling for fragmentation, IPv6 extension chains, path MTU, ICMP errors and quoted translated headers. Decide per supported path whether to forward, translate, reassemble under a bounded budget, or discard with an observable reason. Publish the supported packet/offload matrix. Define slow-path budgets for control traffic and unresolved neighbors, per-tenant flow limits, port exhaustion behavior and counter semantics. Exercise frame-in/frame-out behavior on both address families and translation paths using an independent packet oracle. Treat malformed and oversized input as ordinary parser outcomes.

Specialize the program once per executable release and supported NIC profile. Publish live route, ACL, neighbor and backend data through versioned table handles. A control-plane commit validates all related changes, builds the replacement snapshot off-path and publishes one generation atomically. Readers pin a generation for their packet batch; reclaim it after all readers finish. A BGP withdrawal and a health failure update live state without a binary build. A change to the backend selection algorithm creates a new program generation; active flows retain their recorded bindings.

**One complete flow.** Receive a TCP SYN for a listener. Lookup the connection first; on a miss, consult the current listener generation, select a healthy member and allocate a translated port. Publish forward and reverse entries as one ownership decision before transmission. A returning backend packet uses the reverse entry to recover the original tuple. Mark the backend draining. Subsequent packets on that connection retain the binding and a new connection selects a different member. Race creation on two RX queues and verify a single binding and collision-free reverse lookup. For UDP, document the idle lifetime and prove when the same tuple may legitimately select a new backend.

## Installation and continuity

Start with a portable userspace packet I/O driver for functional qualification. Add an AF_XDP driver for the production queue path with explicit buffer ownership, RSS/queue mapping, supported copy modes and a startup capability probe. Use the same generated packet program through both drivers. Separate management connectivity from the forwarding interfaces; installation validates interface ownership before binding queues. Supply a virtual topology for release qualification, plus a supported NIC/kernel matrix verified on actual hardware.

Persist candidate and committed configurations, peer settings, release digest and leadership generation. Use a third-party quorum lease or equivalent fencing service for an active/standby pair. Define the exact acknowledgment boundary for replicated flow creation. If established-flow continuity is promised, replicate both directions, allocator ownership and expiry before making the first translated packet visible. On loss of quorum fence the old owner and expose degraded status. Specify what already committed flows may do during replication loss. Recovery rebuilds volatile routes and neighbors before advertising readiness. Runbooks cover replacement, failback, rolling upgrade, state-schema compatibility and restoring management access after a rejected configuration.

## Delivery sequence and exit gates

| Stage | Deliverable | Acceptance evidence |
|---|---|---|
| 1. Reference router | Spec, deterministic clock, virtual ports, packet capture/replay, static forwarding, neighbors, MTU and drop reasons | Independent endpoints exchange real traffic through the reference process. Golden captures cover both IP families, control replies and truncation at each supported header boundary. |
| 2. Generated routing appliance | Native parser, route lookup, packet emission, management API/CLI, transactional configuration and persistent boot | Clean install routes traffic through physical ports. Differentially compare packet bytes, egress, counters and table generations under route churn. Reject a bad candidate without interrupting forwarding. |
| 3. Routing peers and full NLB | Generated BGP peer, listener/pool admin, probes, TCP/UDP flows, IPv4/IPv6 translation and draining | Interoperate with an independent routing daemon, withdraw a route under load, exercise forward/reverse translation with independent clients and servers, verify drain, expiry and exhaustion histories. |
| 4. Hardware and availability | Queue driver, multicore ownership, bounded memory pools, standby replication, fencing, rolling upgrades and diagnostics | Kill the active node at allocation, replication and send boundaries. Test asymmetric traffic, queue migration, link failure, partition and recovery. Measure surviving connections and observed disruption against the declared continuity contract. |
| 5. Release | Reproducible package/image, operator manual, supported profiles, captures, benchmark and restore evidence | Use an external traffic generator with mixed frame sizes, long-lived flows and connection churn. Record loss, packets/s, connections/s, latency percentiles, maximum flows, convergence and failover on named hardware. Repeat at capacity and overload; verify management access and bounded resource consumption. |

Change one forwarding policy and one listener selection rule in the specification. With compiler and drivers frozen, rebuild the appliance, verify changed packets and flow choices and replay the unchanged protocol corpus. Qualify dynamic withdrawal and drain separately with the very same binary. Shipping requires both the router and NLB paths, peer interoperability, a clean appliance install and hardware/availability evidence.
