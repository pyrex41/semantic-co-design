# A generated spot trading engine

## Product and deployment

Deliver an operator-run engine for a funded spot account on one named exchange, with multiple instruments, limit orders, cancels, market data, a deployable strategy, pre-trade risk, execution, accounting, reconciliation, reporting and emergency controls. Select a venue and record the dated API version, instrument rules, authentication, session limits, order identity behavior and history retention before implementing its adapter. The release must connect to that venue's actual service. Simulator and recorded-session modes are additional execution modes of the same engine. The initial product uses externally custodied funds and trading-only credentials. Withdrawals, leverage and multi-venue settlement would require separate contracts.

The application source describes feed and execution protocols, session state, book updates, strategy, monetary types, order state machine, risk, ledger, recovery and operator commands. Generate the ingestion, strategy and execution processes, account writer, reconciliation jobs, replay/backtest command, operator API/CLI and reporting executable. Link generic sockets, TLS, secret signing handles, clocks, durable logs and database drivers. Venue field names, cancel semantics and account balance rules belong in generated code. Real-money deployment is a separate operator action after qualification; implementation and tests use isolated accounts and bounded exposure.

## What the author writes

| Module | Ordinary executable behavior | Build-time choices and runtime inputs |
|---|---|---|
| Market and order sessions | Decode messages, authenticate, negotiate subscriptions, detect gaps, re-snapshot and rate-limit requests | Fix venue grammar and supported endpoints; receive live sequences, snapshots, metadata and account events |
| Strategy | Ship one deterministic, configurable inventory-rebalancing strategy with target bands, limit prices, order lifetime and pause/resume commands | Fix strategy program per release; evaluate live prices, freshness, inventory, targets and limits |
| Risk and execution | Quantize orders, reserve assets/fees, admit, reject, route, cancel, expire and reconcile | Fix rules and permitted order types; read current exposure, balances, instrument status, fees and operator overrides |
| Accounting | Book fills, fees, reversals and adjustments with exact amounts and lineage | Fix currency/quantity types and journal schemas; consume venue execution identities and statements |
| Operations | Generate authenticated commands, health, live order/blotter views, balances, exceptions, replay and signed release manifest | Fix interfaces and permissions; supply live account, deployment version and audit identities |

Represent price and quantity as checked integers with explicit scale and rounding side. Derive required intermediate widths from configured instrument bounds. Reject an order on overflow, invalid increments or unavailable metadata. The reference runner executes the exact source with virtual time and recorded feeds; replacing clock, storage and transport drivers connects it to a real account. Compiling fixes the program and venue grammar. Changing a live risk ceiling or disabling an instrument takes effect in the serialized account command stream without rebuilding.

## Ownership, durability and uncertainty

Assign one fenced writer per account; strategies produce intents and never send directly. The account writer serializes intents, fills, cancels, limit changes and operator commands, validates live risk and persists the decision, reservation, client order ID and send intent atomically. Partition feed work by instrument while retaining exchange sequence semantics. Durable recovery state includes raw event provenance, normalized sequence, book validity, outstanding reservations, execution IDs, cash/asset journal, reconciliation cursor, strategy version and timers. Materialized books, positions and reports must rebuild from a documented snapshot plus journal suffix. Publish which clock and event ordering replay uses.

Model order states including pending send, sent/unknown, acknowledged, partially filled, cancel pending, fully filled, cancelled, rejected and reconciliation required. A cancel request does not release an outstanding reservation. Apply fills received during cancel, duplicate reports and late fees according to their identities. A venue snapshot may omit already completed orders; reconciliation must cover open orders, historical fills and balances with overlapping windows. A missing observation leaves the account restricted until resolved. Define trading, cancel-only, paused and reconciliation-required modes. A kill command fences new sends, attempts cancellation and reports outstanding exposure until confirmed.

**Decisive history.** Available buying power is 100 and 60 is already reserved. Submit two independent buy intents requiring 30 each. Only one may reserve. Crash after the exchange accepts its order and before the local acknowledgment. Restart under a new fence; query by the persisted client order identity and reconcile executions before allowing any new exposure. Deliver a partial fill twice, then race the remaining fill against cancellation. Compare the external order count, available/reserved balances, execution IDs, fees, journal and customer-visible status at each step. If the venue cannot identify an unknown send conclusively, the specification parks it for operator resolution. A retry policy cannot manufacture that evidence.

## Delivery sequence and exit gates

| Stage | Deliverable | Acceptance evidence |
|---|---|---|
| 1. Protocol and account contract | Venue capability matrix, exact numeric model, independent ledger oracle, normalized event schema and recorded sessions | Reference engine reconstructs an actual captured book and account history. Detect a missing sequence, a duplicate fill and an unexplained balance difference. |
| 2. Generated sessions and strategy | Native codecs, snapshot/delta recovery, backpressure, strategy timers, virtual clock replay and operator configuration | Replay identical market data through source and native processes; compare every book checkpoint and intent. Inject stale feeds and revisions of instrument precision. |
| 3. Complete order lifecycle | Generated risk/account writer, outbox sender, user feed, amendments where supported, cancel handling and ledger projections | Venue simulator and sandbox exercise timeout-before-send, timeout-after-accept, partial fill, reject, maintenance and leadership loss. Independent reconciliation checks every outcome. |
| 4. Complete operator product | Authenticated order/status/position queries, export, limit administration, kill/resume, manual reconciliation with reason and approvals, alerts and secret rotation | Operators can explain each open reservation and trade from source event to posting. Restart during kill and credential rotation. Restore from backup; verify replay fingerprints and external account state. |
| 5. Release qualification | Signed package, deployment and failover runbooks, metrics and daily independent statements | Benchmark data bursts, queue lag, book staleness, decision-to-send p99, cancel latency and recovery catch-up. Shadow a live feed, qualify a venue-approved test account, then separately authorize a tightly limited live order/cancel/reconciliation cycle. |

Cross-version acceptance changes the strategy's target-band rule and the risk treatment of pending cancels using only application source. Recompile, replay the old journal under its pinned release, and activate the new release at a recorded boundary. Outstanding orders retain their originating identities and obligations. A production release requires named operational ownership, authorized venue access, reconciled account evidence, enforceable exposure limits and a tested stop procedure. Profitability is a separate empirical question from engine correctness.
