# Generated Coinbase Exchange spot engine

The manifest specializes the eight [App Shen](../LANGUAGE.md) modules into the native entries invoked by `engine`. The same entries run under the reference evaluator. The source owns Coinbase request shapes and signing-field names, level-3 book updates, strategy decisions, concurrent account admission, order and cancel state, reconciliation, ledger postings and operator behavior. The Python host serializes calls, commits JSON records and the event log to SQLite, runs authenticated HTTP, and executes generated transport descriptors through a generic TLS and HMAC driver. The release does not carry an evaluator or the Shen sources.

## Build and run

The build needs CPython, Cython 3.1.6 and a C compiler. The package needs the same CPython ABI, SQLite and the OS TLS trust store. Its WebSocket command uses `websocket-client` 1.8.0. The build consumes checked-in source and installed dependencies offline. All examples below use the sandbox public endpoint or local state.

```sh
cd example/trading-engine
python3 check.py
python3 package.py build --out /tmp/coinbase-engine
python3 package.py inspect /tmp/coinbase-engine
printf '{}\n' | /tmp/coinbase-engine/engine --database /tmp/coinbase.sqlite call status
printf '{"kind":"product","product":"BTC-USD"}\n' \
  | /tmp/coinbase-engine/engine --database /tmp/coinbase.sqlite fetch
```

Use `package.py interpret --database PATH call ENTRY` for the same CLI with the reference evaluator. Build with `--sign-key PATH` and use `package.py verify RELEASE --public-key PATH` to verify the signed ownership record and each listed artifact. The acceptance test generates an ephemeral key for this check. Release signing keys and exchange credentials have separate lifecycles.

Each mutating `call` takes a JSON object, a fence via `--fence` and the host's event time in UTC milliseconds. `acquire-writer` takes a strictly increasing `fence` in its input and parks trading until the account reconciles. `start` anchors the account to its opening statement and `sandbox` by default. Set `environment` to `production` only as part of a separately authorized live deployment. Account and transport descriptors are bound to the stored environment. `resume` requires a completed reconciliation.

`serve` starts the loopback JSON API. Its `--credentials` file maps bearer tokens to an `actor` and list of `roles` declared by `access` in the manifest. Use mode `0600`. A `POST /v1/ENTRY` body contains `fence` and `event`. The API checks credentials and roles before invoking the entry. The local CLI uses the operating-system user as the audit actor. Adjustments require two distinct authenticated actors and retain their reason and paired postings. `status`, `order`, `blotter`, `executions`, `journal` and `exceptions` serve operator reporting.

`stream --signing-file PATH --fence N` negotiates the declared `full` feed, fetches snapshots after subscription, consumes sequenced events and invalidates the books when the session ends. `fetch` performs a generated GET request for `product`, `snapshot`, `accounts`, `open-orders`, `fills` or `lookup`. `send --signing-file PATH --fence N` accepts a `client-id`. It claims the persisted intent, then commits an authorization after rechecking the fence, mode, phase, credential epoch and request. The receipt carries a durable attempt identity. Direct `authorize-send`, `send-result` and `cancel-result` calls use the claim output to identify that attempt. The signing file is mode `0600`. It supplies `key`, base64 `secret`, `passphrase`, `scope` and `epoch` for the generic driver. Use `rotate` to record a new epoch and require fresh reconciliation before resuming. The signing file and generated signatures remain outside SQLite and the generated package.

The account operator applies settled private fills using `fill`, and applies a client identity lookup with `order-evidence`. `reconcile` checks each open order identity and terms against local obligations, alongside complete overlapping history and the reported balance, hold and availability. Account queries and evidence submission are scripted operator steps. `tick` expires working orders and reports pending actions. Strategies produce `intent` results for submission through `admit`. `kill` fences later authorizations, releases submits whose dispatch authorization has yet to commit and moves in-flight orders to cancellation. A cancel waits for venue identity so it cannot overtake an unresolved submit. A confirmed terminal order and completeness of settled fills determine final release of the reservation. Outstanding amounts remain visible through restart.

## Exact amounts and recovery

Prices are signed checked cents and base quantities are integers in units of `10^-8` BTC or BCH. Quote cash and fees use `10^-16` USD. Price and quantity parsing permits trailing zeroes beyond the declared scale and rejects any lost nonzero digit. Order inputs must be positive and satisfy the current increment and minimum. Strategy buys round price down, sells round it up, and quantities round down to their increments. Fee reserves round upward to the nearest quote atom. Notional is first formed in `10^-10` USD and then multiplied by `10^6`. The engine bounds the intermediate at `5 × 10^12` and cash at `5 × 10^18` atoms, or USD 500. Each base holding is limited to 100 units. Release bounds include 1,024 resting orders per book, 1,024 account orders and 4,096 settled executions. Invalid precision, missing metadata, bound exhaustion and ambiguity fail closed. Trade limits and instrument controls are serialized with intents and fills.

The SQLite writer persists the event, actor, release, reply and resulting state digest with the new snapshot in the same transaction. `BEGIN IMMEDIATE` orders competing writes. The claim, dispatch authorization and result commit in separate transactions. Committing the authorization is the dispatch boundary. Socket I/O then runs with the writer lock released, allowing kill commands and fills to commit while an authorized request is in flight. Kill can return before a previously authorized request reaches the wire. Its reservation remains visible until a correlated transport outcome or independent venue evidence establishes what happened. A result applies once against current account state when the attempt, writer fence, credential epoch and release activation still match. A crash before authorization leaves a recoverable claim. A crash after authorization leaves the order unknown until client-identity reconciliation, even if the process died before transmitting. A confirmed pre-transmission failure can be requeued. Exchange-side effects and database commits remain separate. Market book ordering uses the venue's per-product sequence. Live book freshness uses the exchange timestamp, so processing a queued frame cannot restore freshness by changing its arrival time. Account replay uses committed journal order and the recorded UTC millisecond clock. A process replacement advances the fence and invalidates the old book. Snapshots and event history can be checked independently with `engine --database PATH replay`.

`backup OUTPUT` uses a consistent SQLite snapshot. Reopen the restored file and run `replay` before resuming. For a compatible source-only release, run `call activate-release --fence N` under the new package at a planned boundary. Orders retain their original release and obligations. On an upgrade or rollback, use `replay --pinned OLD_RELEASE_DIR` to resolve events against both packages. The activated package and source-only strategy or risk changes are recorded in the database.

## Qualification status

`check.py` independently checks the two captured public REST books, reference/native correspondence, a book gap and resnapshot, stale markets, changed instrument precision, integer bounds, buying-power contention, settled execution identity, fill/cancel ordering, exact fees, incomplete reconciliation, and kill and credential-rotation transitions. Separate process tests exercise contention, kill and fill while a submit is stalled, process death around claim, authorization and result commits, ownership signatures, API roles, backup and replay, and source-only upgrade and rollback with orders outstanding. Files under `fixtures/` contain only public data. Private histories are deterministic synthetic sessions.

`python3 check_reachable.py RELEASE` runs just the ledger and recovery laws against a freshly generated package. The ordinary `check.py` gate also runs these laws. The [test-only App Shen program](invariants.shen) reads the persisted account shape and compiles separately from the trading transitions. It checks three asset equations by summing each internal asset account's journal postings from zero, including its opening statement. It also derives each open order's reserve from its remaining quantity and fee budget, sums those obligations per asset, and checks that the held amount stays within the materialized balance. Settled executions must match their venue order and cumulative quantity and fees. Each execution has exactly one base and quote posting pair, and exactly one fee pair when the fee is nonzero. Rejected, duplicate or unlinked direct fills and reconciliation-only observations cannot change the financial projection.

The opening statement introduces assets already held at the venue, with an opposing posting to the opening account. A later deposit, withdrawal or balance correction changes the tracked balance only through a separately approved adjustment with a reason and two distinct actors. Reconciliation observes the venue's balance and restricts trading for unexplained differences without posting them. Proposing or approving an adjustment before initialization returns `opening-statement-required`.

An older release could post an adjustment before initialization and then overwrite the materialized balance with the opening statement. The new release returns `opening-ledger-conflict` if uninitialized state already has a balance or financial postings. It clears unposted historical proposals on successful initialization. For existing databases, run `python3 check_reachable.py --database PATH` on a backup or the read-only database path. This checks the committed snapshot, reports the property result in both modes and exits nonzero on a violation. If it reports a discrepancy, pause trading and preserve the database and pinned releases. Replay against those releases, compare the journal and account to independent venue statements and fills, and restore a verified snapshot or have the ledger repaired under a separate reviewed recovery procedure. The guard and diagnostic leave historical postings intact.

The bounded check enumerates every distinct permutation in two six-event schedules from one initialized account with three orders, one authorized submit with an unresolved response, and one fill identity delivered twice. The schedules cover lookup, submit receipt, cancel, kill, restart, and a reconciliation statement with independently specified venue quantities and balances. Across 720 schedules, the gate evaluates 2,020 distinct prefixes and checks each resulting state in both application and law execution modes. It also replays each committed transition in the SQLite crash and backup histories against both releases when they participated in the trace. Nine deliberately corrupted observations must fail in both law implementations, including a fabricated balance adjustment that still balances its journal and a historical pre-opening adjustment retained for recovery. These bounds cover the listed orders, event alphabets, and persisted crash points.

The installed release has fetched current public sandbox metadata. The reference executable has fetched a current BCH-USD level-3 snapshot from the same sandbox. `python3 benchmark.py` records a bounded local workload with generation, package size, cold startup, durable flood handling, queue lag, decisions and cancels to their simulated transport, and replay. The throughput and latency measurements apply to the recorded host and local workload. Authenticated sandbox feed and order tests require approved Coinbase sandbox credentials and a captured private statement. That work must also qualify pagination and retention, fee and terminal-order responses, reconciling live balance and hold discrepancies, stream burst and failover behavior, and pending work under network partitions. The plan's production deployment, cross-host writer fencing, automated private reconciliation scheduling, daily independent statements and quantified load targets remain open. Release promotion requires those observations and named operational ownership.
